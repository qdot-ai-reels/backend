# 백엔드 구조와 DB 역할

이 문서는 김하영님과 백엔드 작업을 맞추기 위해 작성했습니다. 모든 코드를 한 줄씩 설명하기보다는 주요 파일의 역할, 현재 API 처리 흐름, OpenRouter·S3·PostgreSQL의 역할을 정리합니다.

## 1. 전체 구조

현재 백엔드는 다음 세 가지 외부 요소와 연결될 수 있는 구조입니다.

```text
프론트엔드 또는 APIdog
        |
        v
FastAPI 백엔드
        |
        +-- OpenRouter: 스크립트·영상 생성
        +-- ffprobe: 영상 메타데이터 확인
        +-- S3: 영상 파일 저장 및 접근 URL 발급
        +-- PostgreSQL: 작업 정보와 상태 저장 예정
```

현재 실제로 작동하는 흐름은 다음과 같습니다.

```text
상품 정보
→ OpenRouter 스크립트 생성
→ 스크립트 JSON 검증
→ OpenRouter 영상 생성
→ 생성 완료 상태 확인
→ MP4 다운로드
→ ffprobe로 비율·해상도·길이 확인
→ 성공 또는 재생성 결과 반환
```

현재 이 흐름에서는 PostgreSQL에 데이터를 저장하지 않습니다.

## 2. 주요 파일 역할

### `app/main.py`

FastAPI 애플리케이션의 시작점입니다.

- FastAPI 앱 생성
- CORS 설정
- `/api/v1/reels` 하위 라우터 등록
- `/health` 서버 상태 확인 API 제공

현재 `/health`는 FastAPI가 실행 중인지 확인할 뿐, PostgreSQL 연결 상태까지 확인하지는 않습니다.

### `app/api/v1/script.py`

상품 정보를 받아 광고 스크립트를 생성하는 API입니다.

```text
POST /api/v1/reels/script
```

처리 내용:

1. 상품 정보와 최대 영상 길이를 요청으로 받습니다.
2. `OpenRouterClient`에 스크립트 생성을 요청합니다.
3. 장면 시간, 9:16 비율, 자막 등 스크립트 형식을 검증합니다.
4. 검증된 스크립트 JSON을 응답합니다.

현재는 결과 스크립트를 DB에 저장하지 않고 API 응답으로 바로 반환합니다.

### `app/script_generator.py`

OpenRouter 채팅 API를 호출하고 스크립트 응답을 검증합니다.

- 상품 정보를 프롬프트로 변환
- OpenRouter 모델 호출
- 응답에서 JSON 추출
- `scenes` 존재 여부 확인
- 장면 시간 범위 확인
- 9:16 비율 확인
- 최대 영상 길이 초과 여부 확인
- 형식 오류나 요청 제한 발생 시 대체 모델 재시도

이 파일은 외부 AI 호출과 스크립트 형식 검증을 담당합니다. DB에는 접근하지 않습니다.

### `app/api/v1/video.py`

스크립트 JSON과 상품 이미지로 영상 생성을 요청하는 API입니다.

```text
POST /api/v1/reels/video
```

처리 내용:

1. 스크립트 JSON, 상품 이미지, 해상도, 화면 비율을 요청으로 받습니다.
2. `OpenRouterVideoClient`를 생성합니다.
3. `VideoValidationPipeline`을 실행합니다.
4. 영상 생성, 다운로드, 메타데이터 검증을 진행합니다.
5. 성공 여부, 영상 URL, 비용, 시도 횟수, 검증 결과를 반환합니다.

현재 결과를 DB에 저장하지 않고 API 응답으로 바로 반환합니다.

### `app/video_generator.py`

OpenRouter 영상 생성 API와 통신하는 파일입니다.

- 영상 생성 요청 전송
- 모델, 프롬프트, 길이, 해상도, 비율, 상품 이미지 전달
- 영상 생성 작업 ID와 상태 확인 주소 수신
- 생성 상태 확인 반복
- 완료 후 영상 URL과 비용 수신
- 현재 모델의 지원 영상 길이 확인

영상 생성은 시간이 걸리므로 요청 즉시 MP4가 반환되지 않습니다. 백엔드는 작업 상태를 확인한 뒤 완료되면 영상 URL을 받습니다.

### `app/video_validation_pipeline.py`

영상 생성과 검증, 재생성을 연결하는 핵심 파이프라인입니다.

처리 순서:

1. 스크립트 마지막 장면 종료 시간으로 기대 영상 길이를 계산합니다.
2. 영상 생성 API를 호출합니다.
3. 완성된 영상 URL에서 MP4를 임시 파일로 다운로드합니다.
4. 메타데이터를 읽습니다.
5. 비율·해상도·길이를 검증합니다.
6. 조건을 만족하면 성공 결과를 반환합니다.
7. 조건을 만족하지 않으면 설정된 횟수만큼 영상 생성을 다시 요청합니다.

현재 기본 재시도 설정은 최초 요청을 포함해 최대 2회 실행되는 구조입니다.

### `app/video_metadata.py`

`ffprobe`를 실행해 MP4의 메타데이터를 읽습니다.

- 영상 가로 크기
- 영상 세로 크기
- 영상 길이

현재 Dockerfile에서 `ffmpeg`를 설치하며, 그 안에 포함된 `ffprobe`를 사용합니다.

### `app/video_validator.py`

읽어온 메타데이터를 기준과 비교합니다.

현재 확인하는 항목:

- 화면 비율
- 해상도
- 기대 영상 길이와 실제 영상 길이

영상 속 한글이 정확한지, 상품이 제대로 보이는지, 장면이 스크립트와 일치하는지는 현재 자동 검증하지 않습니다.

### `app/video_generation.py`

영상 생성 결과와 재시도 정책을 다루는 별도 도메인 헬퍼입니다. 현재 실제 HTTP 엔드포인트의 주 흐름은 `video_validation_pipeline.py`를 사용하지만, 이 파일도 검증 결과에 따른 재시도 개념을 표현하고 있습니다.

### `app/core/config.py`

AWS와 S3 환경변수를 읽는 설정 파일입니다.

현재 DB 연결 설정이나 DB 세션 생성은 이 파일에 없습니다.

### `app/core/s3.py`

AWS S3 Presigned URL을 발급하는 코드입니다.

현재는 지정한 S3 객체에 접근할 수 있는 임시 URL을 발급합니다. 실제 생성 MP4를 S3에 업로드하는 기능은 아직 연결되어 있지 않습니다.

### `app/api/v1/reels.py`

초기 더미 영상 생성 API입니다.

```text
POST /api/v1/reels/generate
```

현재는 실제 영상을 생성하지 않고 `dummy_reels.mp4`에 대한 S3 Presigned URL을 반환합니다. 실제 영상 생성 흐름은 `script.py`와 `video.py`에 있습니다.

### `tests/`

스크립트 생성, 영상 생성 요청, 메타데이터 추출, 영상 검증, 재생성 파이프라인을 확인하는 테스트 코드입니다.

외부 API를 실제로 호출하는 대신 요청 형식과 내부 처리 결과를 검증하도록 구성되어 있습니다.

## 3. 현재 PostgreSQL 사용 상태

### 현재 준비되어 있는 것

- `docker-compose.yml`에 PostgreSQL 16 컨테이너가 정의되어 있습니다.
- Docker Compose 프로젝트 이름을 `quedot-reels`로 실행하면 `quedot-reels-db-1` 컨테이너가 시작됩니다.
- `requirements.txt`에 `SQLAlchemy`, `psycopg2-binary`가 포함되어 있습니다.
- PostgreSQL healthcheck로 데이터베이스 프로세스가 살아 있는지는 확인합니다.

### 아직 구현되지 않은 것

- SQLAlchemy 엔진 생성
- DB 세션 생성 및 의존성 주입
- 테이블 모델
- Repository 또는 CRUD 코드
- Alembic 같은 마이그레이션
- API 요청 결과의 DB 저장
- DB 조회 API

따라서 현재 PostgreSQL은 실행 환경에 준비되어 있을 뿐, 현재 스크립트·영상 생성 API의 실제 처리에는 사용되지 않습니다.

## 4. 이 프로젝트에서 DB가 필요한 이유

영상 파일 자체는 S3에 저장하고, DB에는 영상 생성 작업을 설명하는 정보를 저장하는 구조가 적절합니다.

### S3에 저장할 것

- 상품 이미지
- TTS 음성 파일
- 중간 영상
- 최종 MP4 영상

### PostgreSQL에 저장할 것

- 작업 ID
- 상품 정보 또는 상품 ID
- 생성된 스크립트 JSON
- 자막과 후킹 문구
- 현재 작업 상태
- 재시도 횟수
- 생성 비용
- 최종 영상의 S3 주소
- 실패 사유
- 생성 시각과 완료 시각

DB를 사용하는 이유는 영상 생성이 오래 걸리고 한 번의 요청으로 끝나지 않기 때문입니다.

예를 들어 사용자가 영상 생성을 요청하면 처음에는 다음 정보를 저장할 수 있습니다.

```text
작업 ID: 123
상태: PENDING
상품: 미니카 출동팩
재시도 횟수: 0
영상 주소: 없음
```

영상 생성이 진행되면 상태를 바꿀 수 있습니다.

```text
PENDING → PROCESSING → COMPLETED
```

실패하면 다음과 같이 저장할 수 있습니다.

```text
상태: FAILED
재시도 횟수: 1
실패 사유: 영상 길이 검증 실패
```

이렇게 하면 프론트엔드가 요청을 보낸 뒤 결과를 기다리는 동안 현재 상태를 조회할 수 있고, 사용자가 나중에 이전 생성 결과를 다시 확인할 수도 있습니다.

## 5. 현재와 향후 흐름 비교

### 현재

```text
요청
→ 외부 AI API 호출
→ 임시 MP4 다운로드
→ 메타데이터 검증
→ API 응답 반환
→ 임시 파일 삭제
```

### DB와 S3를 연결한 향후 구조

```text
요청
→ DB에 작업 생성(PENDING)
→ 외부 AI API 호출
→ DB 상태 변경(PROCESSING)
→ 영상 다운로드
→ S3 업로드
→ 메타데이터 검증
→ DB에 결과와 S3 URL 저장
→ DB 상태 변경(COMPLETED 또는 FAILED)
→ 프론트엔드에 작업 결과 반환
```

## 6. DB를 추가하는 구현 순서

DB 연동은 PostgreSQL 컨테이너가 실행되는 것만으로 완료되지 않습니다. 백엔드 코드가 DB에 연결하고, 저장할 테이블을 정의하고, API 처리 중 실제로 데이터를 저장해야 합니다.

### 6-1. DB 연결 설정 추가

`.env`에 DB 접속 정보를 설정합니다.

```env
DATABASE_URL=postgresql+psycopg2://사용자:비밀번호@db:5432/데이터베이스명
```

Docker Compose 안에서 실행할 때는 호스트명을 `localhost`가 아니라 PostgreSQL 서비스 이름인 `db`로 사용합니다. 로컬 컴퓨터에서 직접 실행할 때는 `localhost`를 사용할 수 있습니다.

### 6-2. SQLAlchemy 엔진과 세션 생성

DB 연결을 담당하는 파일을 추가합니다.

```text
app/db/
├── session.py       # 엔진과 DB 세션 생성
├── base.py          # 모델 기본 클래스
└── models.py        # 테이블 구조
```

세션은 백엔드 코드가 DB에 질의하거나 데이터를 저장할 때 사용하는 연결 통로입니다. API 요청이 끝나면 세션을 닫도록 관리해야 합니다.

### 6-3. 작업 테이블 정의

우선 영상 생성 작업을 관리하는 테이블 하나부터 시작할 수 있습니다.

```text
generation_jobs
├── id                 # 내부 작업 ID
├── product_id         # 상품 식별자
├── product_data       # 요청 당시 상품 정보(JSON)
├── script             # 생성된 스크립트(JSON)
├── status             # PENDING, PROCESSING, COMPLETED, FAILED
├── attempts           # 현재까지 시도한 횟수
├── total_cost         # 누적 생성 비용
├── video_url          # 최종 S3 URL
├── error_message      # 실패 사유
├── created_at         # 생성 요청 시각
└── completed_at       # 완료 시각
```

스크립트와 상품 정보처럼 구조가 자주 바뀔 수 있는 데이터는 PostgreSQL의 JSON 타입으로 저장하는 방안을 검토할 수 있습니다. 실제 컬럼 구성은 팀에서 필요한 조회 조건을 정한 뒤 확정해야 합니다.

### 6-4. 마이그레이션 추가

테이블을 코드로 정의하는 것과 실제 DB에 테이블을 만드는 것은 별도입니다. Alembic 같은 마이그레이션 도구를 사용해 다음 작업을 관리합니다.

1. 모델 변경 내용을 마이그레이션 파일로 생성합니다.
2. 개발 DB에 마이그레이션을 적용합니다.
3. 팀원이 같은 버전의 테이블을 사용하도록 마이그레이션 파일을 Git에 포함합니다.

### 6-5. 영상 생성 API에 DB 저장 연결

현재 `POST /api/v1/reels/video`는 외부 API를 호출하고 결과를 바로 반환합니다. DB를 연결하면 다음과 같이 바뀝니다.

```text
1. 요청을 받으면 generation_jobs에 PENDING 레코드 생성
2. 외부 영상 생성 직전에 PROCESSING으로 변경
3. 생성·검증 결과와 비용을 저장
4. 성공하면 영상 S3 URL과 함께 COMPLETED로 변경
5. 실패하면 실패 사유와 시도 횟수를 저장하고 FAILED로 변경
6. 프론트엔드에 작업 ID와 현재 결과 반환
```

영상 생성 시간이 길어지면 요청을 계속 기다리는 대신 작업 ID를 먼저 반환하고, 별도의 상태 조회 API를 제공할 수 있습니다.

```text
POST /api/v1/reels/video          # 작업 생성
GET  /api/v1/reels/video/{job_id} # 작업 상태 조회
```

이 구조에서는 프론트엔드가 작업 ID로 상태를 확인하고, `COMPLETED`가 되었을 때 S3 영상 주소를 받아 영상을 재생합니다.

### 6-6. S3 저장과 DB 저장 연결

최종 영상이 생성되면 다음 순서로 처리합니다.

```text
OpenRouter 영상 URL
→ 백엔드가 영상 다운로드
→ S3 업로드
→ S3 객체 주소 생성
→ DB의 video_url에 저장
```

DB에는 MP4 바이너리 자체를 넣지 않고, S3의 파일 주소와 생성 작업 정보를 저장하는 방식이 적절합니다.

## 7. DB 연동 시 김하영님과 결정할 내용

- MVP에서 DB 저장까지 이번 범위에 포함할지
- 작업 생성 API와 상태 조회 API를 분리할지
- 작업 상태 값을 어떤 이름으로 통일할지
- 스크립트와 상품 정보를 JSON으로 저장할지 별도 테이블로 나눌지
- S3 업로드를 영상 검증 전과 후 중 언제 실행할지
- 재시도마다 별도의 시도 이력을 저장할지 누적 횟수만 저장할지
- 생성 비용을 OpenRouter 응답에서 받아 저장할지
- DB 연결 실패 시 외부 영상 생성 요청을 진행하지 않을지

## 8. 김하영님과 확인할 내용

- 작업 상태를 DB에 저장하는 범위를 어디까지로 할지
- 스크립트 JSON 전체를 DB에 저장할지
- 상품 정보는 원본 전체를 저장할지 상품 ID만 저장할지
- 영상 파일은 S3에 저장하고 DB에는 URL만 저장할지
- 재시도할 때 같은 작업 레코드를 갱신할지 시도 기록을 별도로 남길지
- 현재 MVP에서 DB 연동을 포함할지, 우선 외부 API 흐름 검증 후 추가할지

## 9. 요약

현재 코드에서 PostgreSQL은 실행되지만 실제 API가 사용하지는 않습니다. 현재 영상 생성 결과는 API 응답으로 반환되고, 영상 파일은 검증을 위해 임시로만 저장됩니다.

향후 DB는 스크립트, 작업 상태, 재시도 횟수, 비용, S3 영상 주소를 관리하는 역할을 맡게 됩니다. S3가 실제 파일을 보관한다면 PostgreSQL은 그 파일과 생성 작업을 추적하는 관리 장부 역할을 합니다.
